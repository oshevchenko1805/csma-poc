## 1. Источники и правило интерпретации

Числа, знаменатели, статистический статус и допустимые выводы взяты только из замороженного `FINAL_RESULTS_AUDIT.md`. Для проверки того, что именно реализовано в PoC, дополнительно прочитаны текущие конфигурации и исполняемые механизмы (`configs/architecture_*.yaml`, `runners/factory.py`, `runners/coordinator.py`, `decision/recovery.py`, `enforcement/isolation.py`, `enforcement/handlers/*`, `enforcement/command_guard.py`, `attacks/*`). Handoff-файлы не использовались как источник истины.

Ключевое правило согласования: глава 3 должна явно различать (1) целевую архитектурную модель, (2) фактически реализованный PoC и (3) измеренные результаты. Архитектурно желаемое свойство нельзя описывать как реализованный механизм или как эмпирически подтверждённый outcome.

## 2. Итоговое решение

В текущем виде переход к главе 4 заблокирован определениями и причинными формулировками в главе 3. Главные блокеры: смешение coverage и speed; подмена Containment Success термином Isolation Success; расширительная трактовка Recovery Success и MTTR; неверное межархитектурное толкование Total Response Time; `False Positive Blast Radius`; отсутствие зафиксированного статуса гипотез; расхождение описания baseline/PoC с реализацией; причинная атрибуция bundled-конфигураций отдельным recovery actions.

Глава 2 в целом согласуется с frozen audit, поскольку формулирует литературную прогалину и целевую архитектурную задачу, а не заявляет численные результаты. Её нужно лишь удержать от переноса теоретического значения *self-healing* на фактически измеренный уровень PoC.

## 4. Консолидированные замены, обязательные до главы 4

Чтобы не размножать разные определения по 3.4 и 3.5, в тексте должна использоваться одна терминология:

| Нельзя оставлять | Замороженная форма |
|---|---|
| `Isolation Success Rate` как outcome | `Containment Success` — ни один нецелевой UAV не вышел более чем на 15 м off-plan после атаки |
| Time to Isolation как физическое containment | `isolation_announce - detection`; локальный in-process timing; attack n=220, valid-master non-null n=222 |
| Recovery Success как полное/безопасное восстановление | прекращение роста off-plan deviation до конца окна; всегда рядом со Stabilisation Level |
| MTTR как время возврата на маршрут | conditional functional MTTR до начала финального стабильного сегмента; n=267 |
| MTTD как среднее и headline speed | conditional-on-detection median [IQR] + n; данные не показывают общего speed advantage C |
| FP rate без exposure | FP-run prevalence отдельно для clean flights и all valid clean windows |
| False Positive Blast Radius | FP loop depth; C mechanism exploratory, n=2 |
| Phase Divergence / Geometry Deviation | Phase Excess / Geometry Excess по определениям `metrics/coordination.py` |
| Total Response Time как общий A/B/C recovery time | C-only, n=88, attack onset → последняя recovery request/ack |
| causal effect отдельного recovery action | наблюдаемый профиль полной bundled-конфигурации; attack, detection path и action конфаундлены |
| «C виявляє раніше» | дополнительный detection coverage C в заданных security-plane scenarios; не общий speed advantage |
| «C краща в усіх сценаріях» | данные не показывают общего преимущества C в проверенных сценариях |
